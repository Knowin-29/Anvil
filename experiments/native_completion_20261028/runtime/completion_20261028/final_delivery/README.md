# Final model delivery workflow

Prepared during the teacher repair campaign. No formal MOPD model or final upload is implied by the presence of these scripts. CPU checks cover standalone decoder parity, static shard allocation and rejection of smoke/unreviewed packages. Actual final-model GPU execution remains to be validated.

1. Complete qualified formal MOPD. `merge.py --adapter CHECKPOINT --output NEW_MERGED_DIR` verifies its complete checkpoint and creates a separate BF16 copy.
2. `prepare.py --training-run RUN --model NEW_MERGED_DIR --output SPEC.json` binds the exact checkpoint, model metadata, representation and frozen evaluators. Default: 32 native shards, 8 public/general shards.
3. `configs.py --spec SPEC.json --output EVAL_DIR --nodes N` creates a fixed, disjoint partition on N nodes (8 A800 each) and prints DLC commands. Check the entire campaign's active allocation before submitting: maximum 32 GPUs. Config creation does not submit anything.
4. Run every generated node task. Existing complete shards are verified and retained. Native partial outputs use the original explicit-resume rules; corrupt/partial trailing records are preserved for explicit recovery. Public, native and general predictions always reference the same model/spec.
5. `score.py --spec SPEC.json --output EVAL_DIR` checks complete 580,000 native records and all public/general IDs, prediction hashes and metric aggregates; it reruns the unchanged public/general scorers. `final_report.json` includes each paper delta, Location100 and complete RefSpatial results. It does not automatically invent an acceptance tolerance or approve quality.

The campaign has used these validation scores to choose repairs. Report this adaptive selection history; do not describe the same sets as a new blind final test.
6. Run `lineage.py --spec SPEC.json --eligibility ELIGIBILITY.json --output LINEAGE.json` after formal MOPD. It traces the exact initial student, completed MOPD exposures and separate G/S/A teacher ancestry. `exposure_audit.py` checks each completed stage against all updates/ranks. Cross-stage unique records and repetitions are counted only along the selected student lineage. Teacher/control experiments are not added to student exposures. Historical checkpoint-1024 warm starts are disclosed separately; unavailable historical per-row counts remain unknown. The report binds the final spec and every evidence file.
7. Review all seven final benchmarks and native quality honestly. A review JSON uses schema `anvil-final-quality-review-v1`, exact `report_sha256` and `final_spec_sha256`, `accepted`, `rationale`, and one `benchmark_assessments` entry per reported public benchmark. This is an evidence-backed model-quality decision, not a request for additional user authorization.
8. `package.py --spec SPEC.json --report EVAL_DIR/final_report.json --review REVIEW.json --lineage LINEAGE.json --interface-validation VALIDATION.json --output NEW_PACKAGE` copies merged weights, the exact adapter, standalone inference interface, score report, quality assessment and lineage. It writes a hash manifest and model card with actual results. Decoder parity receipts are generated by `validate_cpu.py`; rerun after changing the builder.
9. `upload.py --package NEW_PACKAGE --receipt REMOTE_RECEIPT.json` uses only transient `ANVIL_HF_TOKEN`, explicitly verifies Knowin-29 identity, uploads to Knowin-29/Anvil-MOPD-9B, and verifies every file at the resulting exact commit. No HF login or credential-store modification occurs. LFS files use content SHA256 metadata; non-LFS files are downloaded and hashed. `--verify-revision FULL_COMMIT_SHA` retries only verification.

The final lineage schema is `anvil-final-lineage-audit-v1`, with `state: complete`, `final_spec_sha256`, `initial_sft.training_records: 5220000`, `other_experiment_arms_counted_as_final_training: false`, and `evidence` path/SHA256 bindings. Include the actual initialization chain, each stage's exposure audit, original inventory and separately disclosed supplements. This report has not been created in advance of selecting the final training lineage.

Do not call the campaign complete until the final model's quality is accepted and the full remote-verification receipt exists. No GPU quality or upload success is inferred from CPU preflight checks.
